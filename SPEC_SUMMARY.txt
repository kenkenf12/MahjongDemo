PROJECT OBJECTIVE
─────────────────────────────────────────────────────────────────────────────
Build a browser-based, real-time multiplayer Hong Kong Mahjong game where
four human players can join a shared room from separate devices (mobile or
desktop) over the internet with no server setup or app installation required.

GAME FLOW (Single Round)
─────────────────────────────────────────────────────────────────────────────

1. ROOM CREATION & JOINING
   Player A creates room → Gets room code
   Players B, C, D join with code → See 4 seats fill
   
2. INITIAL DEALING
   Server shuffles 144 tiles
   Dealer (East) gets 14 tiles; others get 13
   Flower/season tiles auto-replaced

3. PLAYER TURNS (repeated)
   East discards → Others can claim (Pong/Kong/Win) or pass
   South draws → Discards → Others can claim
   West draws → Discards → Others can claim
   North draws → Discards → Others can claim
   (Cycle repeats)

4. WINNING CONDITION
   Player forms valid hand (4 melds + 1 pair, minimum 1 fan)
   Fan calculated automatically
   Settlement determined (who pays whom how much)

5. END OF ROUND
   Show result, settlement, updated scores
   Players can start new game or leave


KEY GAME ASSUMPTIONS (Provisional - Need User Confirmation)
─────────────────────────────────────────────────────────────────────────────

Winning Hand Structure
  • 4 melds (Chow, Pong, or Kong) + 1 pair
  • Minimum 1 fan required to declare win

Fan Values
  • Pong (exposed triplet):           1 fan
  • Kong (concealed):                 2 fan
  • Kong (exposed):                   1 fan
  • Flower tile:                      1 fan
  • Season tile:                      1 fan
  • All Simples (2-8 only):          2 fan
  • All Terminals/Honors:            1 fan

Dealer Multiplier
  • Dealer wins:  All losers pay 2× fan
  • Dealer loses: Dealer pays 2× fan to winner
  • Non-dealer wins: All losers pay 1× fan

Turn/Rotation
  • Dealer rotates clockwise on loss
  • Dealer stays on win
  • Chow only available from right neighbor
  • Claim priority: Win > Kong > Pong > Chow

Draw Game
  • If wall exhausted, no winner = all-pass
  • No payments made


TECHNOLOGY STACK
─────────────────────────────────────────────────────────────────────────────

Frontend
  Language:      TypeScript (compiled to ES2020 JavaScript)
  Build Tool:    Webpack or Vite
  Styling:       Pure CSS (Flexbox, Grid, mobile-responsive)
  Framework:     None (vanilla DOM manipulation)
  Hosting:       GitHub Pages (static files)
  
Backend
  Runtime:       Cloudflare Workers
  State:         Cloudflare Durable Objects
  Protocol:      WebSocket (JSON messages)
  Database:      None (ephemeral room state)

Communication
  Client→Server: Commands (draw, discard, claim, win)
  Server→Client: Events (draw_result, player_discarded, state_sync, win)
  Latency:       < 500 ms target

CRITICAL DECISIONS
─────────────────────────────────────────────────────────────────────────────

1. SERVER AUTHORITY
   All game logic runs on server (Durable Object).
   Frontend cannot modify game state.
   Result: No cheating; consistent state across all clients.

2. EPHEMERAL ROOMS
   Game rooms are temporary (no persistent database).
   When room ends, all state is discarded.
   Result: No account system needed; simple deployment.
   Trade-off: No historical records or statistics saved.

3. LIGHTWEIGHT SECURITY
   Room code + session ID (no user accounts or passwords).
   Suitable for casual, trusted group play.
   Not suitable for money wagering or ranked competitive play.

4. VANILLA FRONTEND
   No React/Vue framework; vanilla TypeScript + DOM.
   Keeps bundle size small and architecture transparent.
   Trade-off: More verbose DOM code, but simpler to understand.

5. CLOUDFLARE BACKEND
   Free-tier Cloudflare Workers + Durable Objects.
   No infrastructure setup required by player.
   WebSocket support built-in.

RISKS & MITIGATION
─────────────────────────────────────────────────────────────────────────────

RISK: Rule assumptions are incorrect
  MITIGATION: Get explicit user confirmation before implementation
              Stage 1 testing validates rule logic

RISK: WebSocket connectivity issues on weak networks
  MITIGATION: Implement heartbeat/ping-pong to detect disconnections
              Reconnect with up to 5-minute timeout
              Show connection status to user

RISK: Fan calculation is complex and error-prone
  MITIGATION: Comprehensive unit tests for all fan patterns
              Client-side validation for UX feedback
              Server-side validation for correctness

RISK: Mobile UI is too cramped
  MITIGATION: Priority testing on actual mobile devices (not just browser dev tools)
              Responsive design with media queries
              Large touch targets (44px minimum)

RISK: Deployment fails due to environment/config issues
  MITIGATION: Detailed deployment documentation (DEPLOYMENT.md)
              Test deployment early (Stage 5)
              Fallback to local testing if needed
